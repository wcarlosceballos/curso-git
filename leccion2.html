📗 Lección 2 — Ramas, Merge y Conflictos

📌 Idea central

Una rama es una línea de trabajo paralela. El merge es donde Git te obliga a tomar una decisión explícita: cuando dos personas cambian lo mismo, Git no elige por ti. Entender cómo resolver conflictos es lo que separa a quien usa Git de quien pelea contra Git.

1. ¿Por qué ramas?

Sin ramas trabajas directo sobre main. Si algo sale mal, no hay forma de volver atrás sin romper nada.

main         ──A──B──C──────────────►  (estable, siempre desplegable)
                    \
feature/login       D──E──F──►        (trabajo aislado, se integra después)

Reglas de oro:

  • main siempre debe funcionar. Nunca trabajes directamente encima.
  • Una rama = una tarea o una funcionalidad.
  • La rama vive poco: nace, se integra, se borra.

2. Comandos de ramas

ComandoQué hace
git branch -vListar ramas con su último commit
git switch -c feature/loginCrear y cambiar (moderno)
git switch mainCambiar de rama
git merge feature/loginIntegrar en la rama actual
git branch -d feature/loginBorrar ya integrada (segura)
git branch -D feature/loginBorrar forzando (peligrosa)
git log --graph --oneline --allHistorial como diagrama

Modernización: git switch y git restore reemplazaron a git checkout, que hacía tres cosas distintas a la vez. Usa switch para cambiar de rama y restore para deshacer cambios.

3. El flujo de trabajo típico

git switch main
git pull                              # actualizar antes de crear la rama
git switch -c mejorar-readme

# ... trabajas ...
git add README.md
git commit -m "docs: explicar la instalación paso a paso"

git switch main
git merge mejorar-readme
git push
git branch -d mejorar-readme

Fast-forward: si main no se movió desde que creaste la rama, Git simplemente mueve el puntero — no hay commit de merge. Es el caso ideal.

main         ──A──B──M──────────►
                    \         /
feature/fix         C──D────/

4. Conflictos — la parte que nadie te explica

¿Cuándo ocurre? Cuando Git debe fusionar dos versiones del mismo archivo que tocaron las mismas líneas de forma incompatible.

main         ──A──B──C──►        línea 3: "   hola   "
                    \
feature/fix         D──E──►        línea 3: "   goodbye "

Git no puede decidir cuál de los dos textos es el correcto. Solo tú sabes. Por eso te lo pregunta.

NO hay conflicto cuando cambias archivos distintos, o líneas distintas del mismo archivo.

5. Resolver un conflicto — paso a paso

Paso 1 — Git te avisa:

git merge feature/login

CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.

Paso 2 — Git marca el archivo:

<<<<<<< HEAD
Bienvenido a mi proyecto
=======
Hola, bienvenido a MI proyecto
>>>>>>> feature/login
MarcaSignificado
<<<<<<< HEADEmpieza el conflicto — HEAD es tu rama actual
=======Separador
>>>>>>> ramaFin — la rama que se está integrando

Paso 3 — Editas y decides el resultado final:

# Mi proyecto

Bienvenido a MI proyecto

Borra todas las marcas. Si queda alguna, Git sigue viendo el conflicto.

Paso 4 — Marcas como resuelto y confirmas:

git add README.md          # el add es lo que marca "resuelto"
git commit -m "merge: integrar cambios de feature/login"

⚠️ Error clásico: borras las marcas pero olvidas el git add. Git cree que el conflicto sigue abierto y no te deja commitear. El git add es obligatorio.

6. Deshacer — tres comandos que se confunden

Estos tres no son intercambiables. Confundirlos puede borrar trabajo real:

ComandoQué deshace¿Salva al historial?
git restore archivoDescarta cambios no preparados✅ Sí
git restore --staged archivoSaca el archivo del staging✅ Sí
git revert <hash>Crea un commit nuevo que deshace otro✅ Opción segura
git reset --hard <hash>Borra commits y vuelve atrás❌ No, se pierde para siempre

Regla de la vida real: en repositorio compartido usa revert. Nunca reset --hard sobre main.

git log --oneline                  # busca el hash
git revert a1b2c3d                 # crea un commit que lo revierte

git commit --amend -m "otro mensaje"   # arreglar el mensaje del último

7. Ejemplo completo

git switch -c feature/saludo
echo "Hola, bienvenido a MI proyecto" > README.md
git add README.md
git commit -m "docs: saludo más cercano"

git switch main
echo " # Mi proyecto" > README.md        # ¡misma línea!
git add README.md
git commit -m "docs: agregar título al README"

git merge feature/saludo
# ⚠️ CONFLICT en README.md
# edita, borra marcas, luego:
git add README.md
git commit -m "merge: integrar saludo del proyecto"
🧪 Ejercicio 2 — Ramas y conflicto real
  1. Crea la rama feature/titulo y cambia la primera línea del README.md
  2. Vuelve a main y cambia la misma línea de forma diferente
  3. git merge feature/titulo → observa el conflicto
  4. Lee el README.md y localiza <<<<<<<, =======, >>>>>>>
  5. Decide el texto final y borra todas las marcas
  6. git add README.md y commitea el merge
  7. Verifica con git log --graph --oneline
  8. Borra la rama con git branch -d feature/titulo

🎯 Criterio de éxito: el README final tiene el texto que elegiste, sin marcas, y el grafo muestra la rama integrada.
